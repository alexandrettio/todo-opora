# Опора

Персональное пространство для входящих мыслей, проектов и планирования недели и дня. Серверное API отделено от веб-интерфейса; будущие Telegram и Алиса смогут использовать его же.

## Первая версия

- Быстрый сбор мыслей. Из одной записи можно создать несколько дел и затем закончить разбор.
- Задачи, проекты с подпроектами, идеи, обратимое кладбище.
- Девять сфер, комментарии, дедлайн, дата актуальности, место, теги, плановая длительность.
- Недельные обязательства, включая дерево выбранного проекта.
- Дневной рекомендательный план со стандартными секциями (редактируются в настройках), быстрым добавлением в выбранную секцию; задачи недели доступны для выбора дня.
- Переносы и история. Начало дня — 05:00, недели — суббота 05:00, итоги — в пятницу вечером, Europe/Moscow.
- Выполнение, повторное открытие, необязательный комментарий к результату.
- Закрытие проектов снизу вверх и причины отмены начавшихся недельных обязательств.
- Чтение Google Календаря, выбор календарей, синхронизация, локальные чекбоксы встреч.
- Поиск, фильтрация по сферам, выделение названий без изменений 10 дней.
- Базовая Markdown-выгрузка недели.

Название «Опора» рабочее, его можно изменить.

## Стек и структура

- Backend: Python, Django 5.2 LTS, Django REST Framework, PostgreSQL 18.
- Frontend: React 19, TypeScript, Vite, TanStack Query, Lucide, CSS.
- Развёртывание: Docker Compose, Gunicorn, Caddy с HTTPS.
- Контракт: OpenAPI, `docs/schema.yaml`; интерактивная документация `/api/docs/` после входа.

```text
backend/
  config/              настройки и маршруты
  core/models.py       хранение агрегатов и истории
  core/domain.py       правила дел и планирования
  core/views.py        прикладные сценарии и API
  core/contracts.py    контракты команд и обзорного API
  core/google.py       OAuth и импорт Google Календаря
  core/tests.py        доменные и API-проверки
frontend/src/          веб-интерфейс
scripts/               настройка, запуск, проверки, резервная копия
deploy/                Caddy и сборка веб-контейнера
docs/                 модель, OpenAPI, снимки интерфейса и отчёт проверок
```

Контексты пока реализованы в одном Django-приложении с разделением правил, сценариев, сериализации и интеграции. Это небольшой модульный монолит; выделение отдельных пакетов по контекстам возможно по мере роста.

## Локальный запуск

Требуются Python 3.11+ и Node.js 22+. Для локальной разработки используется SQLite; для сервера — PostgreSQL.

Из корня проекта:

```bash
./start
```

Команда работает из папки проекта; из любой другой папки можно вызвать `start` по полному пути. Остановка — `Ctrl+C`, оба сервера завершаются вместе.

Первый запуск установит отсутствующие зависимости, применит миграции, добавит сферы и предложит создать пользователя. Затем открой `http://127.0.0.1:5173`.

Отдельный запуск после установки:

```bash
DEBUG=1 .venv/bin/python backend/manage.py runserver 127.0.0.1:8000
```

В другом терминале:

```bash
npm run dev --prefix frontend
```

Для локальной проверки с PostgreSQL задай `DATABASE_URL` перед запуском миграций и тестов. Пример формата: `postgresql://user:password@localhost:5432/opora`.

## Развёртывание на сервере

Нужны Linux-сервер, Docker с Compose, домен с DNS-записью на сервер и открытые порты 80/443. База данных и API не публикуют собственные порты наружу.

1. Загрузи содержимое корня проекта в GitHub, затем клонируй репозиторий на сервер:

```bash
git clone <URL-репозитория> opora
cd opora
```

Все дальнейшие команды выполняются из этой папки. Нужен также Python 3 для скрипта настройки. В DNS укажи публичный адрес сервера; если есть AAAA-запись, IPv6 тоже должен вести на этот сервер. Порты 80 и 443 должны быть доступны извне и свободны для Caddy.
2. В папке проекта создай настройки:

```bash
python3 scripts/configure.py
```

Скрипт спросит домен и имя пользователя и создаст `.env` с уникальными ключами и первоначальным паролем. Значения `INITIAL_USERNAME` и `INITIAL_PASSWORD` используются только для первого создания пользователя. Сохрани пароль в своём менеджере паролей.

3. Запусти приложение:

```bash
docker compose up -d --build
```

Миграции, создание сфер и первоначального пользователя выполняются автоматически. Caddy получает сертификат для указанного домена. Открой `https://твой-домен` и войди.

Проверка состояния:

```bash
docker compose ps
docker compose logs --tail=100 api worker web
```

Изменение `INITIAL_PASSWORD` после создания пользователя не меняет его пароль. Для смены используй:

```bash
docker compose exec api python manage.py changepassword <имя-пользователя>
```

Вместо `<имя-пользователя>` укажи имя из `INITIAL_USERNAME`.

После первого запуска можно удалить `INITIAL_PASSWORD` из `.env` и пересоздать контейнеры, предварительно сохранив пароль. Не удаляй `SECRET_KEY` и `TOKEN_ENCRYPTION_KEY`.

## Обновление приложения на сервере

Сначала сохрани резервную копию базы и текущий `.env` в защищённом месте, затем получи изменения и пересобери контейнеры:

```bash
./scripts/backup.sh /защищённая/папка/opora-before-update.dump
git pull --ff-only
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 api worker web
```

Проверь вход, открытие задач и сохранение изменений через браузер. Миграции применяются автоматически при запуске API. При изменениях `.env.example` добавь новые параметры в свой `.env`, сохранив прежние ключи и пароли. Обновление может ненадолго прервать доступ.

Данные PostgreSQL и сертификаты Caddy хранятся в Docker volumes и сохраняются при пересборке. Для обычной остановки используй `docker compose down` **без `-v`**: флаг `-v` удаляет данные. Не меняй имя папки развёртывания без переноса volumes: Compose связывает их с именем проекта.

## Google Календарь

Само приложение готово к OAuth, но подключение требует твоего Google Cloud-проекта и согласия на доступ. Реальные календари не подключаются автоматически.

1. В Google Cloud включи Google Calendar API.
2. Настрой экран согласия OAuth и добавь свой аккаунт как тестового пользователя, если приложение находится в тестовом режиме.
3. Создай OAuth Client типа **Web application**.
4. Добавь точный redirect URI: `https://твой-домен/api/google/callback/`.
5. Укажи в `.env`:

```dotenv
GOOGLE_CLIENT_ID=идентификатор-клиента
GOOGLE_CLIENT_SECRET=секрет-клиента
GOOGLE_REDIRECT_URI=https://твой-домен/api/google/callback/
```

`TOKEN_ENCRYPTION_KEY` уже создаётся скриптом настройки. Это отдельный ключ шифрования токенов Google; его нужно сохранять вместе с резервными копиями секретов.

6. Примени настройки:

```bash
docker compose up -d --force-recreate api worker
```

7. В приложении открой **Настройки → Подключить Google**, дай доступ только на чтение и выбери календари с занятым временем. После изменения выбора нажми **Обновить**.

Календари «без Дамира» / «без Даяна» пока не нужны: условия выполнения и оценка свободного времени отложены.

Импортируются отдельные вхождения повторяющихся встреч: предыдущие 35 и следующие 100 дней. Рабочий процесс обновляет их каждый час, также доступно ручное обновление. Старые импортированные события остаются в базе. Галочки хранятся только в тудушнике и не сбрасываются синхронизацией.

В тестовом режиме Google может требовать повторного согласия после истечения выданного доступа. Приложение показывает ошибку и позволяет переподключиться.

Для локальной разработки используй redirect URI `http://127.0.0.1:5173/api/google/callback/` и передай серверу соответствующие переменные окружения. Локальный запуск сам не читает `.env`; Compose читает его при серверном запуске.

## Резервные копии

Создать копию базы:

```bash
./scripts/backup.sh /путь/в/защищённую/папку/opora.dump
```

Храни копии вне сервера. Отдельно защищённо сохрани `.env`, особенно ключ шифрования токенов. Для ежедневных копий добавь вызов скрипта в расписание сервера с абсолютными путями.

Проверка восстановления выполняется в отдельную пустую базу, а не поверх рабочих данных:

```bash
docker compose exec db createdb -U opora opora_restore_test
docker compose exec -T db pg_restore -U opora -d opora_restore_test --no-owner < /путь/к/opora.dump
```

Проверь наличие данных в восстановленной базе. Конкретную политику хранения и автоматическое копирование во внешнее хранилище нужно настроить на сервере владельца.

### Восстановление рабочей базы

Восстановление заменяет данные приложения. Выполняй его только при необходимости, с проверенной копией; предварительно сделай копию текущего состояния. Используй тот же `.env`, особенно `TOKEN_ENCRYPTION_KEY`.

```bash
docker compose stop web worker api
docker compose up -d db
docker compose exec -T db pg_restore -U opora -d opora --clean --if-exists --no-owner --exit-on-error < /путь/к/opora.dump
docker compose up -d
```

После запуска проверь логи, вход и данные. При ошибке восстановления оставь приложение остановленным до устранения причины. Для отката версии могут потребоваться и прежняя версия кода, и соответствующая резервная копия базы.

## Подготовка к GitHub

В репозитории хранятся `backend/`, `frontend/`, `deploy/`, `scripts/`, `docs/` и корневые настройки. `.gitignore` исключает секреты, локальные базы, зависимости, сборку и `.local/` со старыми рабочими артефактами. Файл `.env.example` содержит только образец настроек.

Перед первой публикацией:

```bash
git init
git add .
git diff --cached --stat
git status --short
```

Проверь состав файлов, затем создай коммит и отправь его в свой репозиторий GitHub. Локальные данные SQLite автоматически на сервер не переносятся: при первом развёртывании создаётся пустая база PostgreSQL.

## Проверки

```bash
./scripts/check.sh
```

Проверяются границы дня/недели, переносы, черновое планирование, выполнение заранее, повторное открытие, наследование планов, причины отмены обязательств, закрытие дерева, восстановление, история прошлой недели, изоляция пользователей, CSRF и сохранение календарных галочек при синхронизации.

## Границы версии

Ещё не реализованы планы месяца/квартала, привычки, таймер, расширенные дашборды и колесо баланса, расчёт времени без детей, Telegram, Алиса и совместное использование. Полного офлайн-режима и синхронизации локальных изменений нет.

Приложение работает по сети с сервером. Данные не сохраняются только в браузере. Все значимые решения проверяются сервером независимо от клиента.
